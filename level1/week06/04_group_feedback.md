### 8. 도메인/저장소 분리 기준

> 도메인 객체는 영속성(Persistence)의 메커니즘으로부터 독립되어야 한다.

→ `도메인과 DTO 의 관계처럼, 의존성 역전을 보장하며, 도메인관 무관한 식별자(PK) 를 사용한다.`

(If-Then) 만약 도메인 객체가 DB 연결 정보나 SQL 쿼리를 직접 알고 있다면

→ Repository 인터페이스를 도입하여 도메인 로직과 데이터 액세스 로직을 엄격히 분리한다.

(기준) 분리 기준: "도메인 객체는 메모리 상에서만 존재하며, 프로그램 종료 시 초기화되는 순수 로직에 집중한다."

(금지) `Board`, `Piece` 등 도메인 엔티티 내부에서 `java.sql` 패키지의 클래스를 직접 참조하거나 의존하지 않는다.

### 9. 저장 경계 규칙

> 저장소의 호출은 도메인 비즈니스 로직을 조율하는 다른 계층의 책임이다.

→ `서비스의 public 메서드 단위가 저장의 경계이며, 각 메서드는 하나의 트랜잭션이며 DB 의 무결성을 보장한다.`

(If-Then) 만약 저장/조회 로직이 장기판의 이동 로직이나 승패 판정 로직과 섞여 있다면

→ 서비스(Service) 계층을 도입하여 도메인 객체에 행위를 시킨 후, 그 결과를 저장소에 전달한다.

(기준) 저장 경계 기준: 도메인은 자신의 상태를 변경할 뿐, 저장되는 시점과 방법은 서비스가 결정한다.

(금지) 컨트롤러나 도메인 객체가 직접 `Repository`의 세부 구현체(예: `JdbcRepository`)를 생성하거나 관리하지 않는다.

### 10. 저장 시점 규칙

> 데이터의 변경은 의미 있는 행위가 완료된 시점에 즉시 반영되어야 한다.

→ `의미있는 변경만을 선택적으로 반영하며, 데이터베이스의 무결성을 보장한다.`

(If-Then) 만약 게임 도중 비정상적인 종료에도 데이터가 유지되어야 한다면

→ 매 턴 종료(기물 이동 성공) 시점마다 변경된 상태를 DB에 저장한다.

(If-Then) 만약 특정 행위(이동, 잡기 등)가 도중 실패하거나 예외가 발생한다면

→ 데이터를 저장하지 않고 이전 상태를 유지하는 트랜잭션 롤백 원칙을 적용한다.

(기준) 저장/조회 시점: 성공적인 행위 단위(Transaction Unit)의 종료 시점에 저장하고, 애플리케이션 시작 또는 '이어하기' 요청 시점에 조회한다.

(금지) 도메인 로직이 수행되는 중간 단계(예: 유효성 검사 직후, 이동 전)에서 불완전한 데이터를 DB에 반영하지 않는다.
